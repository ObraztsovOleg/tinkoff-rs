# Запуск sandbox-стенда через Docker Compose

Нужен Docker с Compose v2+ и Python 3.9+ для подготовки секретов. Rust на хосте
не требуется: бинарник собирается в Linux-образе.

В `compose.yaml` два сервиса:

- `postgres`: PostgreSQL 17, без опубликованного порта;
- `app`: наблюдатель расписания счетов, до 10 runtime (лимит задаётся в панели), веб-страница
  и её сборщик котировок. Все процессы находятся в одном контейнере, поэтому
  страница видит реальные PID стратегий.

Тома `postgres-data` и `campaign-data` сохраняют БД, конфиги, состояние,
журналы, отчёты и графики после пересоздания контейнеров. Docker socket
в контейнеры не передаётся. Подготовка ожидает готовности PostgreSQL через
[healthcheck Compose](https://docs.docker.com/compose/how-tos/startup-order/).

## Новая установка

```sh
python3 scripts/compose-setup.py init
docker compose up -d --build
```

`init` берёт `TINKOFF_TOKEN_SANDBOX` из указанного fish-файла и создаёт отдельные
secret-файлы в игнорируемом Git каталоге `docker/local/secrets/` с правами 0600.
Пароль PostgreSQL генерируется один раз. Токен не попадает в YAML, build context,
аргументы процесса или журнал. Compose монтирует секреты в `/run/secrets/`.
[Как работают secrets Compose](https://docs.docker.com/compose/how-tos/use-secrets/).

На macOS скрипт также экспортирует публичные сертификаты `Russian Trusted`
из доступных связок ключей, включая пользовательскую и системную:
установленные для T‑Invest CA будут доступны Linux-контейнеру. На Linux при
необходимости положите доверенные дополнительные сертификаты в
`docker/local/ca/*.crt` — по одному PEM-сертификату на файл. Проверка TLS включена.

Страница: **http://127.0.0.1:8765**. На первом запуске сначала подбираются
инструменты, создаются sandbox-счета и загружается история; это может занять
несколько минут. Ход подготовки виден через `docker compose logs -f app`.

Ранее разрешённое пользователем переиспользование десяти счетов между 16
сценариями включено по умолчанию. Смена владельца выполняется только после
очистки предыдущего сценария. Для новой кампании это можно запретить переменной
`SANDBOX_ALLOW_ACCOUNT_REUSE=0`; при лимите десяти счетов подготовка 16 сценариев
тогда остановится.

Пустая установка не присваивает счета другой кампании. Если токен уже занят
существующими десятью счетами, перенесите исходное состояние и БД по инструкции
ниже. Одного флага переиспользования для чужих счетов недостаточно.
Если прежняя кампания завершена, вместо переноса можно разрешить взять её
пустые счета: `env SANDBOX_ADOPT_IDLE_ACCOUNTS=1 docker compose up -d --build`.
Счета не закрываются; подробности — в разделе «Новая кампания после
завершённой» [руководства кампании](SANDBOX-CAMPAIGN.ru.md).

`init` также переносит `TINKOFF_TOKEN_PRODUCTION` (из окружения или fish-конфига)
в секрет `tinkoff_token_production`; без переменной секрет пустой и реальные счета
отключены — см. [руководство по реальным счетам](LIVE-TRADING.ru.md).

`init` также создаёт файл профилей ИИ-моделей `docker/local/ai/models.toml`
из примера; токены и модели в нём задаёте вы — см.
[стратегию на ИИ-модели](AI-MODEL.ru.md). Каталог монтируется в контейнер только
для чтения, правки видны без перезапуска.

## Сон компьютера

Стенд работает внутри виртуальной машины colima: пока Mac спит, все стратегии
стоят, а пропущенная торговая сессия не наверстается. Панель показывает такие
интервалы предупреждением «Компьютер спал …». Во время торгов держите Mac
подключённым к сети и с открытой крышкой (или с внешним монитором), а на время
торгов можно запретить сон командой:

```sh
caffeinate -ims
```

Решение на открытии сессии, пропущенное из-за короткого сна или сбоя сети,
стратегия повторяет раз в минуту до конца этой сессии.

## Документы для ИИ-модели

Когда включён портфель с ИИ-моделью, наблюдатель запускает сборщик документов
(`tinkoff-bot collect`, журнал — `/data/logs/collector.log`) и перезапускает его
при сбое; при критически малом месте на диске сборщик останавливается.
Настройки — `docker/local/ai/sources.toml` (создаётся командой
`python3 scripts/compose-setup.py init` из `examples/sources.example.toml`),
подробности — [AI-MODEL.ru.md](AI-MODEL.ru.md#документы).

Поиск по смыслу необязателен и требует места на диске (около 2 ГБ на образ и
модель плюс векторы):

1. В `.env` рядом с `compose.yaml`: `POSTGRES_IMAGE=pgvector/pgvector:0.8.0-pg17`
   (тот же PostgreSQL 17 с расширением; том с данными остаётся).
2. `docker compose --profile embeddings up -d` — служба `embeddings` скачает
   модель `bge-m3`.
3. В `docker/local/ai/sources.toml` раскомментируйте раздел `[embeddings]`.
   Сборщик сам создаст таблицу и индекс и начнёт дописывать векторы.

## Место на диске, обслуживание и резервные копии

Самый дефицитный ресурс стенда — диск Mac: виртуальная машина colima растёт на
нём по мере записи. Панель «Обзор → Хранилище» показывает свободное место на
диске Mac и в томе стенда, размер базы, последнее обслуживание и копии.

- **Контроль места** — раз в 5 минут (`DISK_WATCH_PATHS`, в Compose это
  смонтированный каталог `/run/ai` на диске Mac и том `/data`). Меньше
  `DISK_WARN_GB` (3 ГБ) — предупреждение в панели; меньше `DISK_CRITICAL_GB`
  (1 ГБ) — останавливаются сбор документов и резервные копии. Торговля
  продолжается.
- **Ночное обслуживание** — в 03:30 МСК, вне торгов:
  - отметки плановых проверок риска старше 7 дней удаляются: их идентификаторы
    содержат время и никогда не повторяются; отметки свечей, расписания и
    решений модели остаются — на них опираются прогрев и повтор открытия;
  - замеры доходности старше 30 дней прореживаются до одного в час, старше
    года — до одного в день;
  - записи расходов на модели старше 400 дней удаляются;
  - `VACUUM ANALYZE`, журналы длиннее 50 МБ сжимаются до последних 10 МБ
    (предыдущая часть — в `<имя>.log.1`).

  Сбой повторяется через час.
- **Резервные копии** — служба `backup`: `pg_dump` каждую ночь в 04:00 МСК и при
  запуске, если последней копии больше суток. Копии лежат в томе стенда
  (`/data/backups`), хранятся последние `BACKUP_KEEP` (3). Векторы документов в
  копию не входят: они пересчитываются.
- **Журналы контейнеров** ограничены: до 3 файлов по 20 МБ на службу.

Восстановление из копии (в новую базу):

```sh
docker compose exec backup sh -c 'ls -l /data/backups'
docker compose exec backup sh -c 'PGPASSWORD="$(cat /run/secrets/postgres_password)" createdb restored && PGPASSWORD="$(cat /run/secrets/postgres_password)" pg_restore -d restored /data/backups/<файл>.dump'
```

## Перенос текущей локальной кампании

**Сейчас локальный стенд продолжает работать. Само создание Compose-файла его
не переносит.** Для переноса запустите команды последовательно:

```sh
python3 scripts/sandbox-campaign.py park
python3 scripts/dashboard/server.py stop
python3 scripts/compose-setup.py export
docker compose up -d --build
```

`park` останавливает торговые процессы и проверяет освобождение account leases,
сохраняя позиции, заявки и расписание для восстановления. Для совместимости со
старым наблюдателем сначала приостанавливается его планировщик; после штатной
остановки runtime и проверки БД завершается только процесс планировщика.
Эта команда отличается от `stop`, который запрашивает ликвидацию позиций.

`export` принимает только припаркованную кампанию. Он сохраняет `pg_dump`,
конфиги, журналы и отчёты в `docker/local/import/`, убирает старые PID и локальные
параметры соединения. Идентификаторы счетов, стратегий, заявок и risk epoch
сохраняются. Маркер `MOVED_TO_COMPOSE` запрещает случайный повторный запуск
локального наблюдателя. Исходные данные остаются на месте.

Импорт выполняется только в **новые тома Compose**: PostgreSQL восстанавливает
SQL при первом запуске, приложение копирует подготовленное состояние при первом
создании `/data/campaign.json`. Если этот Compose-проект уже запускался с другими
данными, выберите новое имя, например `docker compose -p tinkoff-import up -d --build`.
Не удаляйте существующие тома ради повторного импорта.

До окончания экспорта можно вернуться к локальному запуску командой
`python3 scripts/sandbox-campaign.py start`. После экспорта не запускайте две
копии кампании на разных БД: account leases действуют внутри одной PostgreSQL.

## Управление

```sh
docker compose ps
docker compose logs -f app
docker compose exec app python3 scripts/sandbox-campaign.py status
# Журнал конкретной стратегии:
docker compose exec app tail -F /data/logs/pairs-trading.log
```

`docker compose stop` / `down` паркуют runtime и сохраняют позиции для
последующего восстановления. **Они не являются ликвидацией портфеля.**
Для завершения тестов и закрытия позиций сначала:

```sh
docker compose exec app python3 scripts/sandbox-campaign.py stop
docker compose exec app python3 scripts/sandbox-campaign.py status
# После phase=complete:
docker compose down
```

Если рынок закрыт, оставьте контейнеры работающими: cleanup продолжится в
доступное окно. После завершения кампании веб-страница остаётся доступной.
`docker compose up -d` возобновляет припаркованный стенд. Маркер `STOP` сохраняется:
после запроса ликвидации возобновляется только cleanup.

Скопировать отчёты на хост:

```sh
docker compose cp app:/data/reports ./sandbox-reports
```

Если 8765 занят, используйте `env DASHBOARD_PORT=8766 docker compose up -d` и
откройте http://127.0.0.1:8766. Веб-порт публикуется только на loopback хоста.
Компьютер и Docker должны оставаться включёнными в торговые сессии.

Управление стратегиями, ручными заявками, бюджетом и рейтингом доступно в той же
панели. См. [руководство управления](SANDBOX-CONTROLS.ru.md). Очередь команд и
настройки сохраняются в PostgreSQL при перезапуске Compose.
