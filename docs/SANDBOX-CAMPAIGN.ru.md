# Живая sandbox-кампания

Весь стенд можно запустить в контейнерах: [инструкция Docker Compose](DOCKER.ru.md).

Кампания проверяет 15 встроенных стратегий и пример `weighted-ensemble` за пять
полных сессий MOEX. История используется только для прогрева; торговые сигналы
возникают из настоящего расписания и потока свечей. Параметры стратегий берутся
из существующих TOML-примеров. Бюджет — 1 000 000 виртуальных рублей на сценарий,
дневной стоп — 5%, максимальная просадка — 25%.

Нужны работающий Docker с образом `postgres:17-bookworm`, Rust и Python 3.9+.
Для текущего macOS-стенда REST-запросы используют `/usr/bin/curl` и установленные
доверенные сертификаты, gRPC — системное хранилище через rustls-native-certs.
Запускатель читает только литеральное присваивание `TINKOFF_TOKEN_SANDBOX` из
`~/.config/fish/conf.d/env.fish`, передавая токен боту как `TINKOFF_TOKEN`.
Токен не записывается в конфиги и не передаётся в аргументах процесса.
Для проверки gRPC, подписок, календаря и прогрева без живых решений используйте
`cargo run -- --config PATH run --startup-only`. Этот режим сохраняет состояние
прогрева и риска, но выходит до восстановления заявок и live-событий.
Прогрев сохраняет свечи пакетами с атомарным checkpoint состояния. Перед
планированием и отправкой заявки проверяются отдельные текущие котировки:
положительная цена, время сделки не старше пяти минут и доступность торгов.
На закрытом рынке разрешён прогрев; исторические цены не используются для заявок.

```sh
cargo build --locked --all-features
python3 scripts/sandbox-campaign.py prepare
python3 scripts/sandbox-campaign.py start
python3 scripts/sandbox-campaign.py status
python3 scripts/sandbox-campaign.py stop
python3 scripts/sandbox-campaign.py archive   # перенести завершённую кампанию в архив
```

`prepare` создаёт отдельный PostgreSQL, счета и конфиги, проверяет историю,
применяет миграции и сохраняет календарь следующих пяти полных сессий.
Повторная подготовка использует уже созданные ресурсы. Неоднозначно завершившееся
пополнение сначала проверяется чтением баланса; торговые mutations не повторяются
вслепую.

На текущем токене API фактически разрешил **10 sandbox-счетов**. По умолчанию
достижение лимита останавливает подготовку. Только после явного разрешения
пользователя можно выполнить:

```sh
python3 scripts/sandbox-campaign.py prepare --allow-account-reuse
```

В этом режиме 16 сценариев распределяются по имеющимся счетам. Одновременно
исполняется не больше четырёх сценариев. Новый владелец допускается только после
успешного `cleanup` предыдущего и `risk-reset` с новым `strategy_id`.
Состояние, заявки и результаты предыдущего сценария сохраняются в PostgreSQL;
прежняя risk epoch экспортируется в отдельный отчёт до смены владельца.

| Полные сессии | Группа |
|---|---|
| 1–2 | pairs-trading, market-intraday-momentum, intraday-same-clock, weighted-ensemble |
| 3 | moving-average-trend, range-breakout, time-series-momentum, cross-sectional-momentum |
| 4 | intermediate-momentum, fifty-two-week-high, residual-momentum, short-term-reversal |
| 5 | low-volatility, betting-against-beta, equal-risk-contribution, volatility-managed |

`start` запускает отдельный процесс наблюдения. Он держит `caffeinate -ims`:
macOS не засыпает по простою, а при питании от сети — и по системному таймеру.
Закрытая крышка без внешнего монитора, работа от батареи, выключение или
перезагрузка всё равно останавливают стратегии; `start` предупреждает, если Mac
работает от батареи. После сбоя повторный `start` подхватывает сохранённые PID и
расписание. Запускатель не продлевает пятисессионное окно, чтобы скрыть
пропущенные проверки.

### Сеть и перезапуски

Стратегии не завершаются при потере сети: runtime пропускает решения без
связи, сам переподключает поток данных, догружает пропущенные свечи и при
долгом простое пересоздаёт сессию (подробно — в разделе «Работа без сети»
[руководства](RUNBOOK.ru.md)). Наблюдатель также переживает временную
недоступность Docker, PostgreSQL и брокерского API: неудачный проход
записывается в `supervisor.log` и повторяется, а аудит брокера при отсутствии
сети откладывается целиком, не тратя минуты на таймауты по каждому счёту.

Аварийный выход runtime перезапускается сразу до трёх раз подряд, затем с
паузой 1, 2, 4, 8 и не более 15 минут — до конца окна когорты, без отказа от
стратегии. Runtime, проработавший 15 минут, снова получает три быстрых
перезапуска. Плановая проверка перезапуска (`verify_restart`) эти попытки не
расходует. Статус «Пауза перед перезапуском» в панели и `retry_at` в `status`
показывают время следующей попытки, `launches` в отчёте — число аварийных
запусков.

### Новая кампания после завершённой

Ничего не удаляется. Завершённая (`phase=complete`) или припаркованная кампания
переносится в архив, после чего готовится новая:

```sh
python3 scripts/dashboard/server.py stop
python3 scripts/sandbox-campaign.py archive
cargo build --locked --all-features
python3 scripts/sandbox-campaign.py prepare --adopt-idle-accounts --allow-account-reuse
python3 scripts/sandbox-campaign.py start
python3 scripts/dashboard/server.py start
```

`archive` переносит `target/sandbox-campaign/` в
`target/sandbox-campaign-archive/<id>/` и отказывается работать, пока запущены
наблюдатель, runtime или панель. Контейнер PostgreSQL прежней кампании, его том
и sandbox-счета остаются нетронутыми.

Если лимит счетов уже занят, `--adopt-idle-accounts` разрешает взять открытые
счета без позиций, блокировок и активных заявок (проверяется через
`GetSandboxPositions` и `GetSandboxOrders`); счета не закрываются и не
переименовываются. Прежний остаток сохраняется, недостающее до 1 000 000 ₽
пополняется один раз. Используйте флаг, только когда другие кампании на этом
токене остановлены: их lease находится в другой базе. Взятые счета перечислены в
`adopted_accounts` файла `campaign.json`.

Для визуального просмотра есть локальная страница:

```sh
python3 scripts/dashboard/server.py start
```

Откройте **http://127.0.0.1:8765**. Здесь показаны расписание, состояние стратегий,
балансы, позиции, заявки, исполнения и операции брокера. Фильтр стратегии
применяется к таблицам; у графика есть отдельный выбор счёта. Переиспользуемые
счета считаются один раз. История операций относится ко всему счёту, поэтому
после передачи владельца в ней остаются операции предыдущего сценария.
Служебные закрытия отмечены отдельно от заявок стратегии.

Нажмите на строку стратегии: откроются её фактический список инструментов,
свечной график выбранного актива и отдельные таблицы исполнений и планов.
Можно выбрать свечи 5, 10 и 30 секунд, 5 и 30 минут, либо дневные.
Быстрые интервалы загружаются только для открытого графика и обновляются через
общий кэш раз в пять секунд; при ограничении API показывается задержка.
Формирующаяся свеча показана бледнее. Подтверждённые исполнения отмечены
треугольниками покупки/продажи; ромбы обозначают сохранённые заявки в плане.
Рыночной заявке не приписывается будущая цена исполнения. Просроченные
неотправленные заявки не считаются действующим планом; неопределённые и принятые
брокером заявки остаются видны до сверки. Последняя целевая доля портфеля
показана отдельно — она не гарантирует сделку.

Если процессы ещё не запущены, страница объясняет ожидание расписания и показывает
время старта каждой группы. Исторические котировки можно смотреть до запуска
стратегии; получение данных для графика не создаёт сигналов и не запускает торговлю.

Страница получает снимки каждые 10 секунд; исходный отчёт обновляется примерно
раз в минуту, снимок брокера — раз в пять минут. Возраст данных указан на странице.
График стоимости включает пополнения и начинает накапливаться с запуска
страницы; до второго снимка показано ожидание, без вымышленной истории.
Накопленные точки сохраняются в `target/sandbox-campaign/dashboard-equity.jsonl`.
HTTP-сервер слушает только `127.0.0.1`; в Compose порт также опубликован на
loopback. Команды сохраняются в PostgreSQL, а торговые действия выполняет Rust
под эксклюзивным владением счётом. Изменяющие запросы требуют локальную сессию,
совпадающий Origin и CSRF-токен. Broker-токен браузеру не передаётся.
Отдельный дочерний сборщик `scripts/dashboard/market_feed.py` обновляет свечи
примерно раз в минуту через `GetCandles`. Он использует тот же безопасный способ
чтения sandbox-токена и передачи заголовка через stdin, что и запускатель.
В браузер токен не передаётся. Котировки сохраняются отдельно в
`reports/market-chart.json` и не подаются в runtime стратегий. При остановке
страницы её сборщик котировок также останавливается.

```sh
python3 scripts/dashboard/server.py status
python3 scripts/dashboard/server.py stop
# Другой локальный порт (если сервер ещё не запущен):
python3 scripts/dashboard/server.py start --port 8766
```

Остановка страницы не останавливает кампанию. После перезагрузки компьютера
страницу нужно запустить заново, как и наблюдатель кампании.

Файлы находятся в игнорируемом Git каталоге `target/sandbox-campaign/`:

- `campaign.json`: календарь, счета, PID, этапы, параметры отдельной БД; права 0600;
- `configs/`: конфиги стратегий без broker-токена;
- `logs/` и `supervisor.log`: runtime, восстановление и служебные закрытия;
- `reports/latest.md`, ежедневные отчёты и `final.md`;
- `reports/database.json` и `broker-latest.json`: durable-состояние, заявки,
  исполнения, портфели и операции из API, включая комиссии и пополнения.

`stop` запрашивает остановку торговых процессов и завершение позиций. Сам SIGINT
боту не закрывает позиции. Служебная команда для конкретного конфига:

```sh
cargo run -- --config target/sandbox-campaign/configs/pairs-trading.toml \
  cleanup --reason 'manual campaign teardown'
```

`cleanup` получает account lease, отменяет активные заявки, сверяет durable
намерения и строит отдельный нулевой maintenance-target. При закрытом рынке или
неопределённом исполнении возвращает ошибку; запускатель повторяет проверку
каждые пять минут. До доказанного пустого портфеля и отсутствия заявок счёт
нельзя передать другому сценарию. Счета, PostgreSQL и том автоматически не удаляются.

В отчёте отдельно учитываются запуск, естественный target и исполнения заявок.
Нулевой target — корректное решение; отсутствие сигнала и округление до нуля не
подтверждают торговое исполнение. Maintenance-заявки не засчитываются в покрытие
стратегии. Пять сессий не гарантируют редкие сигналы или проверку месячного перехода.

Проверки:

```sh
cargo fmt --all --check
cargo test --workspace --all-features --locked
cargo clippy --workspace --all-features --all-targets --locked -- -D warnings
PYTHONPYCACHEPREFIX=target/pycache python3 -m unittest discover -s tests -p 'test_sandbox_*.py'
```

`tests/network_outage.rs` проверяет обрыв HTTP/2 и полное «выключение сети»
через TCP-посредник: поток данных не отдаёт стратегии ни одной ошибки и сам
восстанавливает подписки. `tests/test_sandbox_resilience.py` проверяет
перезапуски, устойчивость наблюдателя, аудит без сети, архив и переиспользование
пустых счетов.

Управление стратегиями, бюджетом и рейтингом описано в
[руководстве панели](SANDBOX-CONTROLS.ru.md).
